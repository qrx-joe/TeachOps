## 2. 使用规则

- 每次协作开始先看 `Question`、`Next to do` 和阻塞项；结束时更新状态、结论与证据链接。
- 状态只使用 `TODO`、`DOING`、`BLOCKED`、`DONE`、`CANCELLED`。
- 已验证结论必须链接到文件、测试输出或运行证据；无法验证的内容写成“未知”或“假设”。
- `Communicating` 记录关键决定、理由和影响，不逐字复制聊天，也不记录 API Key、个人数据等敏感信息。
- `Advice` 分开记录“确定建议”“没有把握的点”“用户可能遗漏的点”，避免把推测包装成结论。
- 已完成事项不删除；按日期归档，保留决策演进过程。

## 7. Advice

### 7.1 我比较确定的建议

1. **先解决证据口径，再扩功能。** 当前最大的可信度风险不是功能少，而是把 fixture replay、目标架构或代码推断说成 live 产品能力。
2. **保留确定性核心。** Evidence、Rule、Revision、Audit、Approval 的状态和约束应继续由可测试代码负责；模型生成只提供候选内容，不能拥有审批权。
3. **框架放在适配层。** AgentTeams 或其他热门框架都应通过稳定接口接入。这样更换运行时不会重写证据、审计和审批规则。
4. **详细注释写“为什么”。** 业务不变量、失败阻断、证据边界、数据清理所有权和非直观权衡需要详细说明；普通语法不逐行翻译。
5. **真实用户证据优先于继续写方案。** 三到五次高质量导师访谈，比新增数据库、RAG 或更多 Agent 更能决定下一阶段是否值得做。

### 7.2 我没有把握的点

- **赛事最终审核口径未知。** 仓库中的提交要求不一定是平台当前最终版本，本次没有登录提交平台核验。
- **AgentTeams 在这台机器上的最终可用性部分未知。** 已安装 stable v1.1.2 且烟雾测试六项 live 通过、四 Agent 在线（2026-08-15），但业务流程运行与长期稳定性仍未取得数据，不能因 smoke test 通过而断言业务 flow 可靠。
- **真实导师是否愿意采用未知。** 目前的用户痛点主要来自方案假设和公开产品分析，没有访谈记录或试用数据。
- **哪种编排框架长期成本最低未知。** 社区热度、功能列表和一次 Demo 都不足以证明维护成本；需要同题 spike 和运行数据。
- **法律适用范围需要专业复核。** 本文档列出工程控制点，不构成法律意见；真实上线地区、用户年龄、数据角色和部署方式会改变义务。

### 7.3 目前容易遗漏的点

- 没有明确的真实数据删除、导出、更正和留存期限流程。
- 没有面向导师的误报/漏报成本定义，也没有规则冲突的人工处理时限。
- 没有版本化的 Prompt、Model、Rule Pack 与评测集组合记录；未来很难解释结果变化来自哪里。
- 没有生产故障恢复目标、成本上限和供应商退出方案。
- 没有无障碍验收和未成年人场景的产品检查清单。
- 没有把“建议被接受”与“教学质量真的提高”分开衡量。
