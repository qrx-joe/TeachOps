# TeachOps 技术选型与工程规范（仓库基线）

> 版本：v1.0（2026-08-15）
> 适用范围：当前 TeachOps 仓库及下一阶段 MVP 的技术决策
> 规范关键词：`MUST` 必须、`SHOULD` 建议、`MAY` 可选
> 文档定位：可版本管理的工程基线。完整目标架构仍见 [《研序 TeachOps 技术实施与工程规范 V1.1》](../研序_TeachOps_技术实施与工程规范_V1.1.docx)。

## 0. 先区分三类事实

| 层次 | 当前状态 | 可以对外声称什么 |
| --- | --- | --- |
| 已实现 | Python 3.11+、标准库确定性流水线、Markdown/JSON 契约、`unittest`、`uv`、正常与缺证据 fixture | 本地确定性规则、证据引用检查、阻断和人工审批关联可重复运行 |
| 已核验且 live（业务流程已运行） | Docker Desktop 可用；AgentTeams stable v1.1.2 已安装；烟雾测试（2026-08-15）、正常流程四产物 + 导师审批（2026-08-16）、异常流程 BLOCKED + Manager 停止（2026-08-16）均为 live（证据见运行证据索引） | 可声称 AgentTeams 环境、smoke test 与正常/异常业务 flow 均已 live 运行；多租户、生产稳定性、质量评测等仍属目标架构 |
| 目标架构 | Web、API、PostgreSQL、对象存储、RAG、可观测性、多租户、生产级 Agent 编排 | 只能称为 design / roadmap，不能称为当前能力 |

任何文档、截图、演示和日志都 `MUST` 保留这三层边界。测试退出码为 0 只证明对应检查通过，不自动证明模型质量、真实用户价值、生产稳定性或合规。

## 1. 技术选型原则

1. **问题优先。** 新技术 `MUST` 对应已验证的用户问题、非功能需求或当前实现阻塞。
2. **模块化单体优先。** 在团队、负载和边界尚未稳定前，不拆微服务；先用清晰模块、端口和适配器获得可替换性。
3. **确定性约束优先于 Prompt。** 状态机、权限、Schema、证据引用、审批门和清理规则 `MUST` 由代码执行；Prompt 只承载开放式判断或生成。
4. **运行时可替换。** Domain / Application 不直接依赖 AgentTeams、LangGraph、CrewAI 或模型供应商 SDK；外部能力经 Port / Adapter 接入。
5. **证据可追溯。** 每次运行 `MUST` 能回答输入版本、规则版本、模型/配置、产物、人工决定和最终状态。
6. **少依赖。** 当前标准库能够清楚完成的工作不新增生产依赖。新增依赖 `MUST` 有 ADR、版本策略、许可证和退出方案。
7. **热度只是信号。** GitHub 关注、发布频率、文档质量和生态广度可进入候选筛选，但不能代替可维护性、安全性和同题验证。

## 2. 当前技术基线

| 领域 | 当前选择 | 原因 | 升级触发条件 |
| --- | --- | --- | --- |
| 语言 | Python `>=3.11` | 与现有 Demo 一致；类型提示、标准库足够完成确定性闭环 | 生产 API、模型 SDK 或异步任务需求明确 |
| 环境与依赖 | `uv` + `pyproject.toml` + `uv.lock` | 可复现；运行零依赖；`python-pptx`（及 lxml/pillow）为 dev 依赖，仅用于生成提交 PPT | 运行期新依赖通过 ADR 后使用 `uv add` / `uv sync` |
| 数据交换 | UTF-8 Markdown + JSON | 人可读、Git diff 友好、便于 Schema 化 | 大对象进入对象存储；关系查询进入 PostgreSQL |
| 测试 | `unittest` + 固定 fixture | 零额外依赖，能验证正常和 BLOCKED 路径 | 用例规模扩大时再评估 `pytest`，不为风格迁移 |
| CLI | `scripts/*.py` | 适合比赛 Demo 与本地复现 | 出现多用户、长任务和权限需求时增加 API / worker |
| Agent 协作 | Agent Identity + Skill Contract；AgentTeams stable v1.1.2 本机安装，smoke test 与正常/异常业务 flow 均已 live（2026-08-15/16） | 角色边界和失败契约已经资产化 | 进入导师试用 MVP 或长任务恢复需求时再做编排框架 spike |
| 前端 / 数据库 / RAG | 未实现 | 当前目标不需要，避免把 roadmap 写成事实 | 真实用户验证明确需要工作台、持久化或检索 |

### 2.1 当前模块边界

```text
demo/input
    ↓
scripts（CLI / 参数与退出码）
    ↓
src/teachops_demo（Evidence → Revision → Audit → Approval → Re-audit）
    ↓
demo/*/output（可追溯产物）

agents/*.md + skills/*/contract.md
    └─ 定义未来编排运行时需要遵守的角色和工具契约
```

- `src/teachops_demo` `MUST NOT` 把 fixture 标为 live，也不得把模型内部知识写成 Evidence。
- `scripts` `SHOULD` 只负责输入输出、参数、日志和退出码，不复制业务规则。
- `demo/*/input` 是测试和演示输入；`expected-output` 是 fixture，不是运行时事实。
- 外部 Agent 框架接入后 `MUST` 调用相同 Application 能力或等价契约，不另造一套业务规则。

## 3. 高热度同类框架参考（2026-08-15 核验）

社区热度变化快，本文不冻结星标数字；只记录可复用的工程能力和当前维护信号。

| 项目 | 值得借鉴 | 对 TeachOps 的判断 |
| --- | --- | --- |
| [CrewAI](https://github.com/crewAIInc/crewAI) | 角色化 Agent、Crew / Flow 编排、较高社区关注 | 适合快速角色协作实验；不能替代 TeachOps 的证据、规则和审批 Domain |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 持久状态、可恢复执行、Human-in-the-loop、图式工作流 | 若下一阶段需要长任务恢复和显式状态图，值得做 spike；不应仅因热度迁移 |
| [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) | 少量核心抽象、handoff、guardrails、sessions、tracing | Python 路线的轻量候选；供应商与模型兼容性需要用实际部署需求评估 |
| [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) | Python/.NET、多 Agent workflow、OpenTelemetry、A2A/MCP | 企业集成候选；原 AutoGen 已进入维护模式，新项目不应再以 AutoGen 作为默认基线 |
| [AgentTeams](https://github.com/agentscope-ai/AgentTeams) | Manager-Workers、Matrix 可见协作、人类介入、共享文件、网关隔离凭据 | 与比赛的“可见协作证据”高度匹配，但基础设施较重；保留适配层并先取得一次 live 运行 |

### 3.1 候选框架必须通过同题 spike

框架选型 `MUST` 使用同一固定课例、同一状态机和同一验收，不用不同 Demo 做主观比较。至少记录：

- 正常、BLOCKED、模型超时、人工驳回后的恢复行为；
- 状态持久化与幂等；
- tracing 是否能关联 `run_id`、`packet_id`、`rule_id`、`evidence_id`；
- 本地安装时间、最低资源、冷启动、单次运行成本；
- 凭据是否对 Worker 可见；
- 单元测试能否绕过真实模型；
- 退出框架时需要重写的代码量。

未通过 spike 前，`MUST NOT` 因“热门”加入生产依赖或重写现有闭环。

## 4. 目标架构：模块化单体 + Ports / Adapters

当真实用户验证进入 MVP 后，推荐按以下依赖方向扩展：

```text
UI / CLI / API
      ↓
Application（用例、状态机、审批、事务）
      ↓
Domain（Evidence、Rule、Revision、Audit、Decision）
      ↑
Ports（Model、Orchestrator、Repository、ObjectStore、Telemetry）
      ↑
Adapters（AgentTeams / 其他 Agent SDK / PostgreSQL / S3 / OTLP）
```

硬规则：

- Domain `MUST NOT` import Web、数据库 ORM、模型 SDK 或 Agent 框架。
- Application `MUST` 负责权限、状态迁移、幂等和人工审批门。
- Adapter `MUST` 把供应商错误转换为稳定的应用错误码，并保留 `retryable` 信息。
- 所有持久化对象 `MUST` 带 `org_id`、稳定 ID、版本和审计时间；引入真实多租户后，授权检查不能只靠 UI。
- 长任务 `MUST` 支持重试不重复落盘；产物先写暂存区，完整成功后原子发布。
- 模型、Prompt、Rule Pack、Schema 和评测集 `MUST` 分别版本化，运行记录保存组合版本。

## 5. Agent / Skill 制作规范

每个 Agent Identity `MUST` 包含：`purpose`、`inputs`、`outputs`、`allowed_actions`、`forbidden_actions`、`handoff_to`、`failure_behavior`。

每个 Skill Contract `MUST` 包含：

- 稳定 `skill_id` 与 SemVer；
- 输入/输出 JSON Schema；
- 调用条件、权限、超时、重试和幂等键；
- 明确错误码与失败时是否允许部分产物；
- 正常、输入缺失、引用失效和模型失败样例；
- 数据、版权、凭据和 Prompt Injection 边界；
- 至少一个不调用真实模型的契约测试。

模型输出 `MUST` 视为不可信输入：先做 Schema 校验、引用完整性和策略校验，再允许进入下游。Agent 无权自行扩大工具权限，也不能把网页、附件或用户输入中的指令当作系统指令。

### 6.1 当前必须保持的安全边界

- 真实学生原始数据默认禁止进入 Demo、Git、Prompt、截图和公开日志。
- API Key 只保存在本机密钥存储、环境变量或受控网关；`MUST NOT` 出现在 Agent 上下文和产物中。
- 课程标准与第三方材料只保留必要短引和来源定位，不复制未授权全文。
- 高风险建议、规则冲突和正式发布 `MUST` 由人类导师确认；系统保存接受、修改、拒绝和理由。
- 删除、覆盖、发布、外发消息和写入外部系统属于高风险动作，`MUST` 二次确认并保留审计记录。

## 7. 数据、API 与可观测性规范

### 7.1 ID 与版本

- 业务对象 ID `MUST` 稳定且不可由展示标题推导。
- Evidence、Revision、Audit、Decision `MUST` 形成可遍历引用链。
- 产物更新 `MUST` 新建版本，不静默覆盖已被审计或批准的内容。
- 时间 `MUST` 使用带时区的 ISO 8601；展示层再转换本地时间。

### 7.2 API

- 未来 HTTP API `SHOULD` 使用 OpenAPI 3.1 和 JSON Schema，错误采用 RFC 9457 `application/problem+json`。
- 错误对象 `MUST` 至少包含稳定 `code`、人可读 `detail`、`trace_id`、`retryable`；字段错误另列。
- 创建和长任务触发接口 `MUST` 支持幂等键；重试不得重复创建运行或应用建议。

### 7.3 日志与 tracing

- 结构化日志 `MUST` 包含 `trace_id`、`run_id`、阶段、状态、耗时和错误码。
- 日志 `MUST NOT` 写完整 Prompt、学生内容、密钥、Cookie 或未经脱敏的附件文本。
- 模型调用记录模型配置别名、Prompt 版本、token/cost/latency 和结果状态；是否保存正文由数据策略控制。
- “live”“fixture replay”“design”是强制证据字段，不允许只靠文件名推断。

## 8. 测试与评测规范

### 8.1 测试分层

1. **单元测试：** 状态迁移、Schema、Evidence 引用、规则、幂等、清理所有权。
2. **契约测试：** Agent / Skill 输入输出、错误码、超时和 Adapter 映射。
3. **fixture 回归：** 正常、缺证据、引用失效、审批过期、模型超时。
4. **集成测试：** 数据库、对象存储、模型网关、编排运行时；使用隔离资源。
5. **评测：** 专家标注集上的证据正确率、规则误报/漏报、建议采纳/修改/拒绝率。
6. **真人验收：** 导师是否能理解依据、处理风险并完成审批；不能由自动测试替代。

### 8.2 变更门禁

- 文档改动：链接、术语、证据类型和当前/目标状态一致。
- 业务代码改动：定向测试 + 全量 `unittest`。
- 跨模块改动：契约测试、类型检查、构建和迁移/回滚演练。
- UI 流程：键盘、可访问名称、错误状态、不同视口和关键端到端路径。
- 模型或 Prompt 变更：固定评测集对比，不能只看少量成功示例。

## 9. 详细注释规范

### 9.1 必须详细注释的内容

| 场景 | 注释必须回答 |
| --- | --- |
| 业务不变量 | 什么条件永远成立，破坏后会造成什么错误 |
| 证据边界 | 为什么该数据只能称为 live / fixture / design |
| 安全或权限门 | 防止哪类越权、泄露或不可逆动作 |
| 降级与失败 | 为什么选择阻断、重试或部分结果，谁负责恢复 |
| 幂等与一致性 | 重复调用为什么安全，写入何时对外可见 |
| 清理与覆盖 | 哪些文件由系统拥有，如何证明可以安全清理 |
| 外部协议陷阱 | 上游版本、字段含义、兼容条件和验证来源 |
| Workaround | 上游 issue / 版本、移除条件、测试保护 |

### 9.2 不应写的注释

- 不逐行翻译语法，例如 `# 创建目录` 紧贴 `mkdir()`。
- 不写已经被类型和命名完整表达的内容。
- 不用注释掩盖过长函数或混乱边界；先拆出可命名的概念。
- 不保留无 owner、issue 或删除条件的 `TODO`。
- 修改行为时同步更新注释和测试；失真的详细注释比没有注释更危险。

### 9.3 Python 示例

```python
def publish_staged_run(stage: Path, output_dir: Path) -> None:
    """原子发布一次完整运行，并只清理本系统拥有的旧产物。

    业务不变量：失败运行不得覆盖上一份可审计结果。清理前必须从
    run_summary.json 证明目录由 TeachOps 生成；不能仅凭文件名相似就删除，
    否则用户放在同一目录的文件可能被误删。

    Raises:
        PipelineError: 暂存产物不完整，或无法证明旧目录所有权。
    """
```

公开模块、类和非显然函数 `SHOULD` 有 docstring。复杂函数内部只在决策点补“为什么”；参数、返回值、异常和副作用应与实际行为一致。

## 10. 可维护性与扩展机制

- 新业务能力先定义 Domain 名词、状态和验收，再决定 UI、数据库或 Agent。
- 一个模块只拥有一类变化原因；跨模块共享的是稳定类型或 Port，不共享内部表结构。
- 每个外部供应商一个 Adapter；供应商字段不直接泄漏到 Domain。
- Feature Flag `MUST` 有 owner、默认值、观测指标和删除日期。
- 数据库迁移 `MUST` 向前兼容并附回滚/恢复说明；破坏性变更分阶段执行。
- 依赖升级按固定节奏进行，安全修复优先；重大版本升级先跑 compatibility note 和回归。
- 关键架构决定写 ADR，至少包含：背景、决定、备选、后果、验证、回滚条件。

## 11. Definition of Done

一项非简单功能只有同时满足以下条件才算完成：

- 需求和不做范围明确；
- 状态、数据、权限和错误契约已定义；
- 实现只修改必要层，非直观逻辑有“为什么”注释；
- 正常、失败、重试和人工覆盖路径有测试；
- 日志与证据类型可区分，未泄露敏感信息；
- README / 模块说明 / 运行手册已同步；
- 已运行与风险相称的验证，并检查实际输出；
- 已知限制、未验证项和回滚方式已记录。

## 12. 下一阶段技术决策顺序

1. 先决定是否需要 live AgentTeams 证据。
2. 再用真实导师访谈冻结下一阶段 MVP。
3. 需要长任务恢复时才做 Agent 编排框架 spike。
4. 需要多用户持久化时再引入 API、PostgreSQL 和对象存储。
5. 需要从大量正式材料检索时再引入 RAG，并先建立检索评测集。
6. 需要学校系统集成时再评估 LTI / OneRoster / Caliper。

这条顺序用于防止“技术很完整，但用户闭环仍未验证”。
