# TeachOps 下一步实施与修复计划

> 版本：v1.0（2026-08-16）  
> 状态：待执行  
> 适用范围：当前比赛型工程原型的修复、AgentTeams live 证据闭环与下一阶段决策  
> 事实基线：以 `docs/运行证据索引.md` 登记的证据类型为准；`live`、`fixture replay`、`design` 不得混用

## 1. 当前判断

TeachOps 已完成一个可复现的比赛型工程原型：四个 Agent Identity、三个 Skill Contract、固定课例输入、确定性 Evidence → Revision → Audit → Approval → Re-audit 闭环、缺课标阻断路径、自动化测试和初赛提交材料均已具备。

当前还不能把项目表述为“原始 PRD 的产品 MVP 已完成”，主要原因如下：

1. AgentTeams 已有 live 烟雾测试记录，但正常流程和缺证据流程尚未形成完整 live 业务证据。
2. README、任务记录、技术基线和提交清单对 AgentTeams 状态的描述不一致。
3. `build-evidence-packet` 对“学情文件缺失”的处理不符合 Skill Contract。
4. 提交预检没有检查跨文档状态一致性、live 证据归档和二进制材料。
5. 工作台、组织权限、通用任务、持久化、版本 Diff/回滚和真实用户评测仍属于后续产品范围。

因此，下一阶段采用以下顺序：

> 先修事实与契约 → 再完成 live 业务闭环 → 再收口提交材料 → 最后决定是否进入导师试用 MVP。

## 2. 本轮目标与完成定义

### 2.1 本轮目标

- 消除仓库内对当前运行状态的互相矛盾表述。
- 修复 Evidence 输入缺失时的失败契约，并增加回归测试。
- 在 AgentTeams 中真实运行正常与异常两条业务流程。
- 归档可复核、已脱敏的 live 证据，并更新提交材料。
- 冻结比赛收尾或导师试用 MVP 的下一阶段方向。

### 2.2 本轮 Definition of Done

本轮只有同时满足以下条件才算完成：

- `docs/运行证据索引.md` 成为 live 状态的唯一事实源，其他材料与其一致。
- 课标或学情文件缺失/不可读时均按契约返回 `BLOCKED`，并列出 `missing_items`。
- 正常和异常两条 AgentTeams 流程都有消息轨迹、业务产物、人工决定或停止记录。
- 所有 live 文件完成脱敏、命名、登记和来源说明。
- 自动化测试、提交预检和文档一致性检查通过。
- Git diff 只包含本轮必要改动，不包含凭据、私有截图或本机配置。
- 项目负责人已书面冻结下一阶段目标和明确不做项。

### 4.2 FIX-002：修复 Evidence 输入缺失契约

#### 问题

`build-evidence-packet` 的契约要求课标或学情文件缺失/不可读时输出 `status=BLOCKED` 和 `missing_items`。当前实现先读取 `learner-summary.json`，学情缺失时会直接抛出 `PipelineError`，无法形成可交给 Manager 和导师的阻断产物。

#### 实现原则

- 在解析文件内容前先统一检查必需 Evidence 输入是否存在且为普通文件。
- 课标缺失、学情缺失、两者同时缺失均返回 `BLOCKED`。
- `missing_items` 必须逐项列出，不用一个泛化错误掩盖多个缺失输入。
- 学情文件存在但 JSON 非法、缺少 `synthetic: true` 或字段质量错误时，继续使用 `E_DATA_QUALITY`，不得误报为文件缺失。
- BLOCKED 运行不得生成修订稿、审计报告或最终稿。
- 不改变正常样例已有输出，除非属于错误修复的必要结果。

#### 需要增加的测试

1. 缺少 `curriculum-source.md` → `BLOCKED`。
2. 缺少 `learner-summary.json` → `BLOCKED`。
3. 两个 Evidence 输入同时缺失 → `BLOCKED` 且列出两项。
4. 学情 JSON 非法 → `E_DATA_QUALITY` 或稳定的数据解析错误，不产生 READY 包。
5. 学情缺少 `synthetic: true` → 继续拒绝建包。
6. BLOCKED 重跑会清理 TeachOps 拥有的旧下游产物，但不触碰用户文件。

#### 验证

```powershell
$env:UV_CACHE_DIR='.uv-cache'
uv run python -m unittest discover -s tests -v
uv run python scripts/run_demo.py normal
uv run python scripts/run_demo.py missing-evidence
git diff --check
```

通过标准：所有测试通过；正常链路仍完成两次审计；异常链路只产生 Evidence Packet 和 run summary；Git diff 无意外产物变化。

### 4.3 LIVE-001：运行 AgentTeams 正常业务流程

#### 目标

证明 Manager、Evidence、Design、Audit 四个角色实际参与同一课例，而不是用 fixture 或日志文本模拟多 Agent 协作。

#### 执行步骤

1. 按 `docs/agentteams-运行手册.md` 核对 AgentTeams 版本、团队成员和挂载的 Identity/Skill。
2. 在 Team Room 发起正常课例任务，只传递仓库输入文件引用和必要状态。
3. Evidence Agent 生成 READY Evidence Packet。
4. Design Agent 基于 READY Packet 生成带 Evidence ID 的 revision。
5. Audit Agent 逐条输出 rule_id、结果和 Evidence ID。
6. Manager 将 WARN/FAIL 和产物引用转交导师，不得自行批准。
7. 项目负责人作出批准、附条件批准、驳回或补证决定。
8. 如决定要求修改，修改后重新审计，保存最终结果。

#### 必须留存的证据

- Team Room 四 Agent 成员与角色配置截图。
- Manager 的任务拆解和分派记录。
- Evidence、Design、Audit 的实际消息轨迹。
- `evidence_packet.json`、`revision.md`、`audit_report.json`。
- 人工审批决定及其绑定的 `report_id`。
- 运行时间、模型别名、结果状态和失败/重试说明。

#### 停止线

- Evidence Packet 为 BLOCKED 时不得继续调用 Design。
- Evidence ID 不可验证时不得把审计标为全 PASS。
- AgentTeams 或模型失败时保留已完成步骤并标记失败，不用 fixture 补齐 live 产物。
- 不在消息、截图、产物或 Git 中保存 API Key、Cookie、账号信息或真实学生数据。

#### 验收标准

- `docs/运行证据索引.md` 的 L4 更新为完成，并链接到实际脱敏文件。
- 产物内证据类型明确为 `live`，且能对应 Team Room 中的真实运行。
- 审批决定引用本次真实审计报告，不复用 fixture 的静态 `report_id`。

### 4.4 LIVE-002：运行 AgentTeams 缺证据异常流程

#### 目标

证明系统在真实多 Agent 环境中能因为关键课标证据缺失而停止，而不是只在本地 Python fixture 中停止。

#### 执行步骤

1. 使用 `demo/missing-evidence-case/input/` 发起任务。
2. Evidence Agent 输出 BLOCKED Packet 和缺失清单。
3. Manager 转达阻断原因和补证要求。
4. 确认 Design 与 Audit 没有被调用，没有产生伪造的下游产物。

#### 验收标准

- `docs/运行证据索引.md` 的 L5 更新为完成。
- 消息轨迹能证明 Manager 在 Evidence 后停止。
- live 目录中不存在该次运行的 revision 或 audit 成功产物。
- 用户可清楚看到缺什么、为什么停止、补证后如何重跑。

### 4.6 DEC-001：冻结下一阶段目标

比赛材料完成后，在以下方向中只选择一个作为下一阶段：

#### 方向 A：比赛收尾

- 目标：完成提交、保存回执、冻结当前版本。
- 明确不做：Web、数据库、RAG、编排框架迁移、更多课例。
- 完成标准：提交状态确认成功，仓库打标签或记录冻结 commit。

#### 方向 B：导师可试用 MVP

- 目标：让 3–5 名导师能用固定流程完成一次预审并给出反馈。
- 首期范围：任务输入、Evidence、候选修订、Audit、人工决定、导出审核包。
- 明确不做：复杂 LMS 集成、自动规则学习、大规模多租户和区域部署。
- 完成标准：形成一页阶段决策，写明目标用户、核心场景、两周验收、明确不做和终止条件。

### 4.7 MVP-001：导师访谈与首批评测集

仅在 DEC-001 选择导师可试用 MVP 后执行。

#### 用户验证

- 访谈 3–5 名师范院校或教师培训导师。
- 核对预审频率、最耗时环节、常见错误、证据要求和审批习惯。
- 不问泛化的“你会不会用 AI”，而是让导师回忆最近一次真实预审任务。

#### 评测集

- 准备至少 10 个公开、授权或明确合成的教学设计样例。
- 每条 P0 Rule 至少包含 3 个正例、3 个反例和 1 个边界/NA 例。
- 加入缺课标、错误字段、冲突规则、无来源资源和模型超时等污染样例。
- 由至少 1 名导师标注关键风险、建议接受/修改/拒绝结果。

#### 验收指标

- 证据引用正确率。
- 规则命中的误报与漏报。
- 建议直接接受、修改后采用、拒绝的比例。
- 导师完成一次任务的耗时与主要卡点。
- 未经人工审批进入正式发布的次数必须为 0。

### 4.8 ENG-001：增加 CI 与持续门禁

#### 建议门禁

- 全量 `unittest`。
- `scripts/preflight_check.py`。
- `git diff --check`。
- 文档证据类型一致性检查。
- fixture 中 Evidence ID、rule_id 和审批 `report_id` 的引用完整性检查。

#### 边界

- CI 通过只证明所列检查通过，不证明 AgentTeams live、教学质量、真实用户价值或生产稳定性。
- live 集成测试需要独立凭据和隔离环境，不应把长期密钥写入仓库或普通日志。

## 5. 证据与文件留存规则

| 类型 | 允许的内容 | 禁止的内容 | 建议位置 |
| --- | --- | --- | --- |
| `live` | 本次真实运行的脱敏截图、产物、轨迹摘要 | fixture 冒充 live、凭据、个人信息 | `evidence/` |
| `fixture replay` | 固定输入与可复现期望输出 | 声称真实 Agent/模型已运行 | `demo/*/expected-output/`、`deterministic-output/` |
| `design` | Agent Identity、Skill Contract、方案与 roadmap | 表述为已上线能力 | `agents/`、`skills/`、`docs/` |
| private | 未脱敏原始截图、提交回执 | 提交 Git 或公开分享 | `evidence/private/`、`submission/receipts/` |

新增 live 证据时必须记录：获取时间、运行标识、证据类型、来源步骤、脱敏说明、关联产物和已知限制。

## 6. 风险与处理方式

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 文档状态再次漂移 | 对外表述失真 | 单一事实源 + 自动一致性检查 |
| live 流程失败后用 fixture 补图 | 证据失信 | 明确失败并保留停止点，不伪造后续产物 |
| 修复 BLOCKED 行为改变已有输出 | 回归或材料漂移 | 先补测试，再做最小修改，检查 diff |
| 截图泄露账号或 Key | 安全事故 | 原图只进 private，脱敏后再归档 |
| 比赛收尾期间扩展产品范围 | 延误提交 | SUB-001 前冻结新功能 |
| 自动规则被误认为教学质量判断 | 过度承诺 | 材料中持续声明结构审计边界，补导师评测 |
